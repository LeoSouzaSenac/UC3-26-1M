Prancha 01 / 08 — Bloco 1

Aula 1 — Introdução a Banco de Dados

Antes de escrever a primeira linha de SQL, você precisa entender três coisas: o que é um dado, onde ele mora, e por que existe uma linguagem inteira só para cuidar dele. É isso que fazemos nesta aula.

1.1 — Dado, informação e conhecimento não são a mesma coisa

É comum usar essas três palavras como sinônimos, mas em tecnologia da informação elas representam degraus diferentes de uma escada:

Exemplo

Dado é solto e sem contexto: 28. Informação é o dado organizado com significado: "a temperatura hoje é 28°C". Conhecimento é o que você faz com essa informação: "28°C é quente, vou levar uma roupa mais leve".

Um banco de dados trabalha na primeira camada dessa escada: ele armazena e organiza dados. Quem transforma esses dados em informação útil, na maioria das vezes, é a aplicação (o site, o sistema, o app) que está por cima do banco — mas para isso acontecer bem, o banco precisa estar muito bem estruturado. É aí que entra o trabalho do profissional de UC3.

1.2 — O que é um Banco de Dados e o que é um SGBD

Um banco de dados é, de forma simples, um conjunto organizado de dados relacionados entre si, guardados de forma permanente (não somem quando você desliga o computador). Pense numa grande "biblioteca de fichários": cada fichário guarda um tipo de informação (clientes, produtos, pedidos), e as fichas dentro dele seguem sempre o mesmo padrão.

Só que ninguém manuseia esses fichários "na mão". Existe um programa especializado só para isso: o SGBD (Sistema Gerenciador de Banco de Dados). É o SGBD que garante que dois usuários não vão bagunçar o mesmo dado ao mesmo tempo, que ninguém sem permissão vai ler informação sigilosa, e que, se a luz cair no meio de uma gravação, o dado não fica corrompido.

Analogia

Se o banco de dados é a biblioteca, o SGBD é o bibliotecário: ele sabe exatamente onde cada livro está, empresta e devolve livros de forma organizada, e não deixa duas pessoas rasgarem a mesma página ao mesmo tempo.

Exemplos de SGBDs que você vai ouvir falar (e usar) o curso inteiro: MySQL, PostgreSQL, Oracle Database e SQL Server. Todos eles "falam" a mesma língua de base — o SQL — mas cada um tem seus próprios sotaques e recursos extras.

1.3 — Banco de dados relacional × não-relacional

Existem duas grandes famílias de bancos de dados, e é essencial saber diferenciá-las logo no início do curso.

Banco de dados relacional

Organiza tudo em tabelas, como planilhas conectadas entre si. Cada tabela tem colunas fixas (nome, e-mail, telefone) e cada linha é um registro (uma pessoa, um produto). As tabelas se conectam por chaves estrangeiras — vamos estudar isso a fundo na Aula 3. É o modelo mais usado no mercado, e é o foco desta UC.

Banco de dados não-relacional (NoSQL)

Não obriga uma estrutura fixa de tabelas. Os dados podem ser guardados como documentos soltos (parecido com um arquivo JSON), pares de chave-valor, ou grafos de conexões. É muito usado quando os dados mudam de formato com frequência ou quando o volume é gigantesco (redes sociais, sensores IoT).

Analogia

O banco relacional é um arquivo de escritório: gavetas etiquetadas, pastas no mesmo formato, tudo padronizado. O banco não-relacional é uma caixa de sapatos onde cada papel pode ter um formato diferente — mais flexível, porém mais difícil de garantir que "está tudo igual".

1.4 — Uma linha do tempo rápida do SQL

Entender de onde o SQL veio ajuda a entender por que ele é do jeito que é.

1970

O artigo de Edgar Codd

O matemático Edgar F. Codd, pesquisador da IBM, publica um artigo propondo o modelo relacional — a base teórica de tudo que estudamos nesta UC.

1974

Nasce o SEQUEL

Pesquisadores da IBM criam a linguagem SEQUEL (depois renomeada para SQL) para "conversar" com bancos relacionais usando frases parecidas com inglês comum.

1979

Primeiro SGBD comercial

A Oracle lança a primeira versão comercial de um SGBD relacional com suporte a SQL.

1986

Vira padrão internacional

O SQL se torna um padrão reconhecido pela ANSI e, depois, pela ISO — por isso o comando SELECT funciona quase igual em qualquer SGBD relacional do mundo.

Hoje

Ainda reinando

Mais de 50 anos depois, o SQL continua sendo a linguagem mais usada para lidar com dados estruturados — é isso que você vai dominar ao longo desta UC.

Ao longo da UC3 você vai alternar entre algumas ferramentas. Não precisa decorar agora, só reconhecer o nome:

  • MySQL Workbench — interface visual para desenhar, consultar e administrar bancos MySQL.
  • SQL Developer e SQL Plus — ferramentas usadas para administrar bancos Oracle: uma com interface gráfica, outra em linha de comando.
  • Um software de modelagem, como o próprio MySQL Workbench ou o draw.io, para desenhar o banco antes de criá-lo de verdade (isso é assunto da Aula 3).
Fica de olho

Repare que já apareceram três siglas parecidas: SQL (a linguagem), SGBD (o programa que gerencia o banco) e MySQL (um SGBD específico que "fala" SQL). É normal confundir no início — releia esta seção se precisar.

Aula 2 — Modelagem Conceitual do Banco de Dados

Nenhum engenheiro começa a construir um prédio sem antes desenhar a planta. Nesta aula, aprendemos a "plantar" um banco de dados no papel — entender o que o cliente precisa, documentar isso e preparar o terreno para o desenho do MER, que vem na próxima aula.

2.1 — Por que modelar antes de programar?

É tentador abrir o SGBD e sair criando tabelas "no improviso". O problema é que, sem planejamento, é quase certo que você vai precisar refazer tudo depois que perceber um relacionamento que esqueceu, ou uma informação que faltou.

Analogia

Construir um banco de dados sem modelar antes é como erguer uma casa sem planta: pode até ficar de pé, mas na hora de passar o encanamento você descobre que não sobrou espaço para os canos — e vai ter que quebrar parede. No banco de dados, "quebrar parede" significa migrar dados de produção, correndo o risco de perder informação.

Por isso, o processo de modelagem passa por três grandes etapas, do mais abstrato para o mais concreto: modelo conceitual (o que estudamos aqui — sem se preocupar ainda com o SGBD específico), modelo lógico (já pensando em tabelas e tipos de dado) e modelo físico (o banco realmente criado, com os comandos SQL rodados). Esta aula foca no primeiro passo.

2.2 — Levantamento de requisitos

Tudo começa conversando com quem vai usar o sistema — o stakeholder. O objetivo é descobrir os requisitos: o que o sistema precisa fazer e como ele precisa se comportar.

Os requisitos se dividem em dois tipos:

  • Requisito funcional: descreve uma ação que o sistema deve executar. Exemplo: "o sistema deve permitir cadastrar um novo aluno".
  • Requisito não funcional: descreve uma característica de qualidade, não uma ação. Exemplo: "o cadastro de aluno deve ser concluído em menos de 2 segundos" ou "os dados dos alunos devem ficar criptografados".
Exemplo prático

Imagine que você está modelando o banco de uma locadora de bicicletas. Ao entrevistar o dono, você anota:

  • Funcional: "preciso saber quais bicicletas estão emprestadas agora".
  • Funcional: "preciso cobrar uma multa se a bicicleta voltar atrasada".
  • Não funcional: "o sistema precisa funcionar mesmo sem internet na loja".

2.3 — Dicionário de dados

Depois de levantar os requisitos, é hora de listar, de forma organizada, cada informação (campo) que o sistema vai precisar guardar. Esse documento se chama dicionário de dados. Ele funciona como um "glossário oficial" do projeto: todo mundo da equipe consulta o mesmo documento para saber exatamente o nome e o formato de cada campo.

CampoTipoTamanhoDescrição

2.4 — Teoria dos conjuntos aplicada a banco de dados

Pode parecer estranho falar de matemática numa aula de banco de dados, mas o modelo relacional inteiro nasceu de conceitos de teoria dos conjuntos. Uma tabela, no fundo, é tratada como um conjunto de linhas. Isso vai explicar, lá na frente, por que comandos SQL como UNION e INTERSECT têm esse nome:

  • União — junta os elementos de dois conjuntos, sem repetir.
  • Interseção — traz só os elementos que existem nos dois conjuntos ao mesmo tempo.
  • Diferença — traz os elementos que existem em um conjunto, mas não no outro.
Analogia

Imagine a lista de alunos que fazem Inglês e a lista de alunos que fazem Robótica. A união das duas listas é "todo mundo que faz pelo menos uma das duas". A interseção é "quem faz as duas ao mesmo tempo". A diferença (Inglês menos Robótica) é "quem faz só Inglês".

Guarde essa ideia — ela volta com tudo na Aula 9 do nosso curso, quando estudarmos JOINs de verdade em SQL.

2.5 — Tipos de dados e domínio de um atributo

Cada informação que vamos guardar tem um tipo (número, texto, data...) e um domínio — ou seja, os valores que ela pode legitimamente assumir. Definir o domínio ainda na modelagem conceitual evita bancos de dados "bagunçados" no futuro.

Exemplo

O campo status da nossa tabela de bicicletas tem domínio limitado: só pode ser "disponível", "emprestada" ou "manutenção" — nunca, por exemplo, "amarela". Já decidir isso agora evita que, no futuro, alguém digite valores inconsistentes ali dentro.

2.6 — Integridade referencial (uma primeira olhada)

Integridade referencial é o princípio que garante que as conexões entre tabelas nunca fiquem "quebradas". Se um empréstimo de bicicleta referencia a bicicleta de id_bicicleta = 12, a integridade referencial garante que essa bicicleta 12 realmente existe na tabela de bicicletas — e impede, por exemplo, que alguém apague a bicicleta 12 enquanto ela ainda está emprestada.

Vamos aprofundar esse conceito na Aula 3, quando falarmos de chaves primárias e estrangeiras — por enquanto, guarde a ideia central: nenhuma referência pode apontar para o nada.

Prancha 03 / 08 — Bloco 1

Aula 3 — Modelo Entidade-Relacionamento (MER)

Chegou a hora de transformar o dicionário de dados e os requisitos da Aula 2 em um desenho. O MER é o "mapa" visual do banco: mostra quais informações existem, como elas se agrupam e como se conectam — tudo isso antes de criar uma única tabela de verdade.

3.1 — O que é uma entidade

Uma entidade representa algo do mundo real (ou até abstrato) sobre o qual queremos guardar dados: um Aluno, um Produto, um Pedido, uma Bicicleta. No desenho do MER, cada entidade vira um retângulo. Mais para frente, cada entidade normalmente vira uma tabela no banco de dados de verdade.

Exemplo

No sistema da nossa locadora de bicicletas, entidades naturais seriam: Bicicleta, Cliente e Empréstimo.

3.2 — Atributos: o que a entidade "sabe" sobre si mesma

Cada entidade tem atributos: as informações que descrevem aquela entidade. A entidade Cliente pode ter os atributos nome, CPF, telefone. Existem alguns tipos especiais de atributo que vale a pena conhecer:

  • Atributo simples: não pode ser dividido. Ex.: CPF.
  • Atributo composto: pode ser dividido em partes menores. Ex.: endereço pode virar rua, número, cidade.
  • Atributo multivalorado: pode ter mais de um valor para a mesma entidade. Ex.: um Cliente pode ter vários telefones.
  • Atributo derivado: pode ser calculado a partir de outro. Ex.: idade pode ser derivada da data de nascimento.

3.3 — Chaves: como identificar um registro sem confusão

Numa turma de 40 alunos, pode existir mais de um "João Silva". Por isso, toda entidade precisa de um jeito de identificar cada registro de forma única — isso se chama chave.

  • Chave candidata: qualquer atributo que poderia, sozinho, identificar o registro de forma única. Um aluno pode ter tanto o CPF quanto a matrícula como chaves candidatas.
  • Chave primária: a chave candidata que escolhemos oficialmente para representar o registro. Geralmente é um código simples, como id_aluno.
  • Chave estrangeira: um campo que "empresta" a chave primária de outra entidade, criando a conexão entre as duas. É assim que um Empréstimo sabe a qual Bicicleta ele se refere.
Exemplo

Na tabela Empréstimo, o campo id_emprestimo é a chave primária dela mesma. Os campos id_bicicleta e id_cliente, dentro dessa mesma tabela, são chaves estrangeiras — eles apontam para a chave primária das tabelas Bicicleta e Cliente.

3.4 — Relacionamentos e seu grau

Um relacionamento é a conexão entre duas (ou mais) entidades — no desenho, vira um losango ligando os retângulos. O grau do relacionamento indica quantas entidades participam dele:

  • Unário: a entidade se relaciona com ela mesma. Ex.: um Funcionário é "supervisor" de outro Funcionário.
  • Binário: o mais comum — duas entidades se relacionam. Ex.: Cliente faz Empréstimo.
  • Ternário: três entidades participam do mesmo relacionamento. Ex.: um Professor ministra uma Disciplina em uma Turma.

3.5 — Cardinalidade: quantos para quantos?

A cardinalidade é uma das partes mais importantes (e mais cobradas em prova!) do MER. Ela responde: "quantos registros de uma entidade podem se conectar a quantos registros de outra?"

TipoDescriçãoExemplo
1:1 (um para um)Um registro de A se relaciona com no máximo um registro de B, e vice-versa.Uma Pessoa tem um Passaporte; um Passaporte pertence a uma Pessoa.
1:N (um para muitos)Um registro de A pode se relacionar com vários registros de B, mas cada B se liga a apenas um A.Um Cliente pode ter vários Empréstimos; cada Empréstimo pertence a um único Cliente.
N:N (muitos para muitos)Vários registros de A se relacionam com vários registros de B.Um Aluno pode cursar várias Disciplinas; cada Disciplina tem vários Alunos.
Fica de olho

Relacionamentos N:N não podem ser implementados diretamente numa tabela — eles exigem a criação de uma tabela associativa (também chamada de tabela de junção) para funcionar no banco físico. Vamos ver isso na prática mais adiante no curso.

3.6 — Entidades fortes e fracas

Uma entidade forte existe por conta própria e tem sua própria chave primária (ex.: Cliente). Uma entidade fraca só existe se estiver associada a uma entidade forte — ela depende da outra para "fazer sentido". Ex.: os Dependentes de um funcionário só existem no sistema porque o Funcionário existe; se o Funcionário for removido, os Dependentes dele também deixam de fazer sentido.

Estudo de caso

Aula 4 — Normalização

Fechando o Bloco 1: agora que sabemos desenhar entidades e relacionamentos, precisamos garantir que as tabelas resultantes sejam "saudáveis" — sem repetição desnecessária de dados e sem armadilhas escondidas. Esse processo de organização se chama normalização.

4.1 — O problema da redundância

Imagine a tabela abaixo, construída "no impulso", sem nenhuma modelagem prévia — um erro clássico de quem pula direto para o SQL sem passar pela Aula 2 e pela Aula 3:

id_pedidoclientetelefone_clienteprodutopreço
1Ana Souza51 9999-0001Mouse45,00
2Ana Souza51 9999-0001Teclado120,00
3Ana Souza51 9999-0001Monitor800,00

Repare no problema: o nome e o telefone da Ana estão redundantes — repetidos em toda linha. Se o telefone da Ana mudar, alguém vai precisar atualizar as três linhas. E se esquecer uma? O banco fica com dados contraditórios.

4.2 — Dependência funcional: a base da normalização

Dizemos que existe uma dependência funcional quando, sabendo o valor de um atributo, conseguimos determinar o valor de outro. No exemplo acima, o telefone_cliente depende do cliente — não do pedido. É essa dependência "no lugar errado" que gera a redundância.

4.3 — As três anomalias

Tabelas mal normalizadas sofrem de três tipos de problema, conhecidos como anomalias:

  • Anomalia de inserção: para cadastrar um cliente novo que ainda não comprou nada, você não tem "onde" colocá-lo, porque a tabela só existe atrelada a pedidos.
  • Anomalia de atualização: mudar o telefone da Ana exige atualizar três linhas — esquecer uma gera inconsistência.
  • Anomalia de exclusão: se a Ana cancelar o único pedido dela (id 1), e essa linha for apagada, perdemos o telefone dela junto — mesmo que ela continue sendo cliente.

4.4 — Primeira Forma Normal (1FN)

Uma tabela está na Primeira Forma Normal quando cada célula guarda um único valor (nada de "listas dentro da célula") e não existem grupos de colunas repetidas.

Antes (viola a 1FN)

telefones: "51 9999-0001, 51 9999-0002" — dois telefones espremidos numa célula só.

Depois (respeitando a 1FN)

Cria-se uma tabela separada Telefone (id_telefone, id_cliente, numero), com uma linha para cada telefone. Assim cada célula guarda um único valor, e um cliente pode ter quantos telefones precisar.

4.5 — Segunda Forma Normal (2FN)

Para estar na Segunda Forma Normal, a tabela precisa, primeiro, já estar na 1FN. Além disso, todo atributo precisa depender da chave primária inteira — não apenas de parte dela. Esse problema só aparece quando a chave primária é composta por mais de um campo.

Exemplo

Imagine uma tabela com chave composta (id_pedido, id_produto) guardando também o nome_produto. O nome_produto depende só de id_produto, não do id_pedido — ou seja, depende de parte da chave, não da chave inteira. Isso viola a 2FN. A solução é mover nome_produto para uma tabela Produto separada.

4.6 — Terceira Forma Normal (3FN)

Para estar na Terceira Forma Normal, a tabela precisa já estar na 2FN, e nenhum atributo pode depender de outro atributo que não seja a chave — isso se chama dependência transitiva.

Exemplo

Numa tabela Aluno (id_aluno, nome, id_cidade, nome_cidade), o campo nome_cidade depende de id_cidade, que por sua vez depende de id_aluno — uma dependência em cadeia. Isso viola a 3FN. A solução é criar uma tabela Cidade separada (id_cidade, nome_cidade), e a tabela Aluno guarda só a chave estrangeira id_cidade.

4.7 — Resultado final: a tabela do pedido, normalizada

Aplicando as três formas normais no nosso exemplo inicial, chegamos a três tabelas enxutas e sem redundância:

ClientePedidoProduto
id_cliente, nome, telefoneid_pedido, id_cliente (FK), id_produto (FK)id_produto, nome, preço

Agora, se o telefone da Ana mudar, atualiza-se em um único lugar. Se ela cancelar um pedido, o cadastro dela como cliente continua intacto. É essa robustez que a normalização entrega.

Nota rápida sobre "desnormalizar"

Em sistemas com altíssimo volume de leitura, às vezes engenheiros optam por desnormalizar propositalmente parte do banco (reintroduzir alguma redundância controlada) para ganhar velocidade de consulta. Isso é um assunto avançado — por enquanto, o mais importante é dominar bem a normalização "pelo livro" antes de aprender quando quebrar a regra.

Aula 5 — Modelo Lógico

Esta é a aula-ponte: pegamos o MER desenhado na Aula 3, já limpo pela normalização da Aula 4, e o traduzimos para uma linguagem que qualquer SGBD entende: tabelas, colunas, tipos de dado e restrições. A partir daqui você já pensa "de olho" no MySQL Workbench, a ferramenta que vamos usar no laboratório.

5.1 — Onde estamos: conceitual → lógico → físico

Vale relembrar rapidinho os três níveis de modelagem que citamos lá na Aula 2:

  • Modelo conceitual (Aulas 2 e 3): entidades, atributos e relacionamentos, sem se importar com qual SGBD será usado. É o "o quê".
  • Modelo lógico (esta aula): já pensa em tabelas, colunas, tipos de dado e chaves — mas ainda de forma independente de fabricante. É o "como, em teoria".
  • Modelo físico (Aula 6 em diante, com DDL): o banco realmente criado dentro de um SGBD específico, com sintaxe exata daquele produto. É o "como, na prática".
Analogia

Se o modelo conceitual é o esboço de um móvel feito à mão livre, o modelo lógico é o desenho técnico com medidas — já sabemos a largura de cada gaveta, mas ainda não escolhemos se o móvel vai ser fabricado em MDF ou madeira maciça. Essa escolha do "material" (o SGBD específico) é o modelo físico.

5.2 — Traduzindo entidades e atributos em tabelas e colunas

A tradução do MER para o modelo lógico segue algumas regras bem diretas:

  • Toda entidade vira uma tabela.
  • Todo atributo simples vira uma coluna daquela tabela.
  • Todo atributo composto é "achatado": em vez de uma coluna endereço, criam-se colunas separadas rua, numero, cidade.
  • Todo atributo multivalorado vira uma tabela própria, ligada à tabela original por chave estrangeira (é exatamente o que fizemos com os telefones do cliente na Aula 4).
  • Atributos derivados normalmente não viram coluna — calculamos na hora da consulta, para não guardar um dado que pode ficar desatualizado.

5.3 — Traduzindo relacionamentos e cardinalidade

Cada tipo de cardinalidade que vimos na Aula 3 se traduz de um jeito diferente:

CardinalidadeComo vira tabela
1:1A chave primária de uma das tabelas é repetida como chave estrangeira única na outra — ou, em muitos casos, as duas entidades são fundidas numa tabela só.
1:NA chave primária do lado "1" vira chave estrangeira na tabela do lado "N". Foi o que fizemos com Cliente (1) e Empréstimo (N).
N:NCria-se uma tabela associativa nova, contendo as chaves estrangeiras das duas tabelas envolvidas (e, se precisar, atributos próprios do relacionamento, como "data_matricula").
Exemplo — N:N virando tabela

Lembra do relacionamento Aluno–Disciplina (N:N) da Aula 3? No modelo lógico ele vira a tabela Matricula: id_matricula (PK), id_aluno (FK), id_disciplina (FK), data_matricula. Cada linha representa "este aluno está matriculado nesta disciplina".

5.4 — Chaves e restrições (constraints)

No modelo lógico já formalizamos as regras que o banco vai obrigar sozinho, sem depender da aplicação para "lembrar" de validar. Essas regras se chamam constraints (restrições):

  • PRIMARY KEY — marca a chave primária da tabela.
  • FOREIGN KEY — marca uma coluna como chave estrangeira, amarrada a outra tabela.
  • NOT NULL — obriga que aquela coluna sempre tenha um valor preenchido.
  • UNIQUE — garante que aquele valor nunca se repete entre as linhas (ex.: e-mail de login).
  • DEFAULT — define um valor automático quando nada é informado (ex.: status DEFAULT 'ativo').
  • CHECK — valida uma condição customizada (ex.: preco > 0).

Antes de sair criando tabelas no Workbench, combine um padrão com a equipe — isso evita um banco "poliglota" onde cada tabela segue uma regra diferente. Sugestão de convenção, que vamos seguir no curso:

  • Nomes de tabela no snake_case, no singular: cliente, pedido, item_pedido (não Clientes nem tblCliente).
  • Chave primária sempre chamada id, ou id_<tabela> quando referenciada como chave estrangeira em outra tabela: id_cliente.
  • Tabelas associativas (N:N) recebem um nome que descreve a ação/relação: matricula, e não algo como aluno_disciplina — embora ambos funcionem, nomes descritivos ajudam a leitura.

5.7 — Conhecendo o MySQL Workbench

  • SQL Editor — a tela onde, a partir da Aula 6, vamos escrever comandos SQL na mão (DDL, DML, DQL).
Analogia

Pense no EER Diagram do Workbench como uma prancheta digital: você desenha as tabelas como se estivesse desenhando o MER da Aula 3, só que já com tipos de dado e restrições configurados em cada coluna. Aula 6 — DDL: Criando a Estrutura do Banco

Chegou a hora de sair do papel. Tudo que desenhamos no modelo lógico (Aula 5) agora vira comando SQL de verdade, rodando no MySQL Workbench. Nesta aula usamos a DDL — a "linguagem de construção" do banco.

6.1 — As famílias de comando do SQL

O SQL não é uma linguagem única e genérica — ele se divide em "famílias" de comando, cada uma com um trabalho específico. Nesta e nas próximas duas aulas, vamos conhecer as três mais usadas no dia a dia:

  • DDL (Data Definition Language) — define a estrutura: criar tabela, mudar coluna, apagar tabela. É o assunto desta aula.
  • DML (Data Manipulation Language) — mexe no conteúdo: inserir, atualizar, apagar linhas. Assunto da Aula 7.
  • DQL (Data Query Language) — consulta dados sem alterar nada. Assunto da Aula 8.
Analogia

Se o banco de dados é uma casa: DDL é o pedreiro levantando paredes e cômodos; DML é a família colocando móveis, trocando de lugar ou tirando algo de dentro de casa; DQL é simplesmente olhar o que já está lá dentro, sem mexer em nada.

6.2 — Criando e usando um banco de dados

Antes de criar qualquer tabela, precisamos criar o "container" que vai guardar todas elas: o banco de dados em si.

-- Cria o banco de dados, se ele ainda não existir
CREATE DATABASE IF NOT EXISTS biblioteca;

-- Diz ao MySQL Workbench: "a partir de agora, todo comando é dentro deste banco"
USE biblioteca;

O USE é fácil de esquecer, mas é essencial: sem ele, o SGBD não sabe em qual banco você quer criar as tabelas — e, se você tiver vários bancos no mesmo servidor, pode acabar criando tabela no lugar errado.

6.3 — CREATE TABLE: o comando mais importante desta aula

O CREATE TABLE cria uma tabela nova, definindo cada coluna, o tipo de dado dela e as restrições (constraints) que vimos na Aula 5. Vamos criar a tabela aluno do nosso estudo de caso da biblioteca:

CREATE TABLE aluno (
  id_aluno INT AUTO_INCREMENT PRIMARY KEY,
  nome VARCHAR(100) NOT NULL,
  turma VARCHAR(20)
);

Repare no AUTO_INCREMENT: ele faz o MySQL numerar os alunos sozinho (1, 2, 3...) sem que você precise informar o número na hora de cadastrar. É quase sempre usado junto com a chave primária.

Agora as outras duas tabelas do modelo lógico da Aula 5, já com chave estrangeira:

CREATE TABLE livro (
  id_livro INT AUTO_INCREMENT PRIMARY KEY,
  titulo VARCHAR(150) NOT NULL,
  autor VARCHAR(100)
);

CREATE TABLE emprestimo (
  id_emprestimo INT AUTO_INCREMENT PRIMARY KEY,
  id_aluno INT NOT NULL,
  id_livro INT NOT NULL,
  data_emprestimo DATE NOT NULL,
  data_devolucao DATE,
  FOREIGN KEY (id_aluno) REFERENCES aluno(id_aluno),
  FOREIGN KEY (id_livro) REFERENCES livro(id_livro)
);

Cada FOREIGN KEY avisa ao MySQL: "esta coluna aponta para a chave primária de outra tabela — não deixe ela apontar para algo que não existe". É a integridade referencial da Aula 2, agora sendo obrigada pelo próprio banco.

6.4 — Mais algumas constraints úteis no CREATE TABLE

Além de PRIMARY KEY, NOT NULL e FOREIGN KEY, vale conhecer mais três, direto na criação da tabela:

CREATE TABLE usuario (
  id_usuario INT AUTO_INCREMENT PRIMARY KEY,
  email VARCHAR(120) NOT NULL UNIQUE,
  status VARCHAR(20) DEFAULT 'ativo',
  idade INT CHECK (idade >= 0)
);
  • UNIQUE — nunca deixa dois usuários terem o mesmo e-mail.
  • DEFAULT 'ativo' — se ninguém informar o status na hora de cadastrar, o MySQL já preenche com "ativo" sozinho.
  • CHECK (idade >= 0) — impede que alguém salve uma idade negativa, sem precisar validar isso na aplicação.

6.5 — ALTER TABLE: mudando uma tabela que já existe

Nem sempre acertamos tudo de primeira. O ALTER TABLE serve para mudar uma tabela que já foi criada, sem precisar apagar e recriar do zero (e sem perder os dados que já estão lá dentro).

-- Adicionar uma coluna nova
ALTER TABLE aluno ADD COLUMN email VARCHAR(120);

-- Mudar o tipo (ou o tamanho) de uma coluna que já existe
ALTER TABLE aluno MODIFY COLUMN nome VARCHAR(150);

-- Renomear uma coluna
ALTER TABLE aluno RENAME COLUMN turma TO turma_atual;

-- Remover uma coluna que não é mais usada
ALTER TABLE aluno DROP COLUMN email;

-- Adicionar uma constraint depois que a tabela já existe
ALTER TABLE aluno ADD CONSTRAINT uq_nome UNIQUE (nome);
Exemplo prático

A biblioteca decidiu que agora quer guardar o telefone do aluno. Em vez de apagar a tabela inteira e recriar (perdendo todos os alunos já cadastrados), basta rodar: ALTER TABLE aluno ADD COLUMN telefone VARCHAR(20);

6.6 — DROP: apagando de vez

DROP remove completamente uma tabela (ou um banco inteiro) — estrutura e dados juntos, sem volta.

-- Apaga a tabela inteira (estrutura + todos os dados)
DROP TABLE IF EXISTS emprestimo;

-- Apaga o banco de dados inteiro, com todas as tabelas dentro dele
DROP DATABASE IF EXISTS biblioteca;

O IF EXISTS evita que o SQL dê erro caso a tabela (ou banco) já não exista mais — é uma boa prática usar sempre.

Fica de olho

DROP TABLE não tem "lixeira": uma vez executado, os dados se foram. Sempre confira duas vezes o nome da tabela antes de rodar um DROP — principalmente em um banco de produção, com dados reais de verdade.

6.7 — TRUNCATE TABLE: esvaziando sem apagar a estrutura

TRUNCATE é um meio-termo interessante: apaga todas as linhas de uma tabela, mas mantém a estrutura dela (colunas, tipos, constraints) intacta — como se a tabela tivesse acabado de ser criada, vazia.

Aula 7 — DML: Manipulando os Dados

Com as tabelas já criadas na Aula 6, chegou a hora de colocar gente e livro de verdade dentro delas. Nesta aula usamos a DML — os três comandos que inserem, atualizam e apagam linhas dentro de uma tabela que já existe.

7.1 — Os três comandos da DML

São só três, e cada um faz exatamente uma coisa:

  • INSERT INTO — coloca uma linha nova na tabela.
  • UPDATE — muda o valor de uma ou mais colunas em linhas que já existem.
  • DELETE — remove linhas inteiras da tabela.

Repare que nenhum dos três muda a estrutura da tabela — as colunas continuam as mesmas, só o conteúdo (as linhas) é que muda.

7.2 — INSERT INTO: colocando dados na tabela

A forma mais segura de inserir é sempre listando o nome das colunas explicitamente:

INSERT INTO aluno (nome, turma)
VALUES ('Bruno Lima', 'DS-2026');

Repare que id_aluno nem aparece — como ele é AUTO_INCREMENT, o próprio MySQL gera esse número sozinho.

Fica de olho

É possível inserir sem listar as colunas: INSERT INTO aluno VALUES (NULL, 'Bruno Lima', 'DS-2026');. Só que aí você precisa acertar a ordem exata de todas as colunas da tabela, incluindo o id. Um erro de ordem, e o dado vai parar na coluna errada sem o MySQL avisar. Por isso, listar as colunas é sempre mais seguro.

Também dá para inserir várias linhas de uma vez só, em um único comando:

INSERT INTO livro (titulo, autor) VALUES
('Dom Casmurro', 'Machado de Assis'),
('O Cortiço', 'Aluísio Azevedo'),
('Vidas Secas', 'Graciliano Ramos');
Exemplo

Inserindo um empréstimo, ligando um aluno a um livro que já existem: INSERT INTO emprestimo (id_aluno, id_livro, data_emprestimo) VALUES (1, 2, '2026-08-04');. Como id_aluno e id_livro são chaves estrangeiras, o MySQL só aceita esse INSERT se o aluno 1 e o livro 2 realmente existirem nas tabelas de origem.

7.3 — UPDATE: alterando dados que já existem

O UPDATE muda o valor de uma ou mais colunas, nas linhas que você escolher com WHERE:

UPDATE aluno
SET turma = 'DS-2027'
WHERE id_aluno = 1;

Dá para mudar várias colunas de uma vez, separando por vírgula:

UPDATE emprestimo
SET data_devolucao = '2026-08-20'
WHERE id_emprestimo = 5;
Fica de olho — o erro mais perigoso da DML

Se você esquecer o WHERE, o UPDATE muda a coluna em todas as linhas da tabela. UPDATE aluno SET turma = 'DS-2027'; sem WHERE colocaria todo mundo na mesma turma de uma vez. Sempre confira o WHERE antes de rodar um UPDATE — em bancos de produção, um UPDATE sem WHERE pode ser catastrófico.

7.4 — DELETE: removendo linhas

O DELETE apaga linhas inteiras, também escolhidas com WHERE:

DELETE FROM emprestimo
WHERE id_emprestimo = 5;
Fica de olho

Assim como no UPDATE, esquecer o WHERE no DELETE apaga todas as linhas da tabela — mas, ao contrário do TRUNCATE (Aula 6), o DELETE ainda permite escolher exatamente quais linhas remover.

7.5 — Boa prática: testar o filtro com SELECT antes

Como o WHERE do UPDATE e do DELETE não tem "desfazer", uma prática comum entre desenvolvedores é rodar primeiro um SELECT com o mesmo filtro, só para conferir visualmente quais linhas seriam afetadas, e só depois trocar o SELECT * pelo comando de verdade:

-- 1) Primeiro, confira quem seria afetado
SELECT * FROM aluno WHERE turma = 'DS-2026';

-- 2) Se a lista bateu com o esperado, agora sim rode o comando real
DELETE FROM aluno WHERE turma = 'DS-2026';

Vamos estudar o SELECT a fundo já na próxima aula — mas adiantar essa dica agora evita muita dor de cabeça na hora de praticar UPDATE e DELETE.

Aula 8 — DQL Básico: Consultando os Dados

Chegamos ao comando mais usado no dia a dia de quem trabalha com banco de dados: o SELECT. Nesta aula aprendemos a consultar dados — filtrar, ordenar, limitar e resumir — tudo isso ainda dentro de uma única tabela por vez. Consultas que juntam várias tabelas ao mesmo tempo (JOIN) ficam para uma aula futura.

8.1 — O que é DQL

A DQL tem um único comando principal: SELECT. Diferente de DDL e DML, o SELECT nunca muda nada no banco — ele só lê e devolve o resultado para você.

8.2 — SELECT básico: escolhendo o que ver

-- Traz TODAS as colunas de TODAS as linhas da tabela
SELECT * FROM aluno;

-- Traz só as colunas que interessam
SELECT nome, turma FROM aluno;

O * (asterisco) significa "todas as colunas". É prático para explorar uma tabela, mas em sistemas de verdade é mais comum listar só as colunas necessárias — traz menos dado desnecessário pela rede.

Também dá para dar um "apelido" a uma coluna no resultado, usando AS:

SELECT nome AS nome_do_aluno, turma AS turma_atual
FROM aluno;

8.3 — WHERE: filtrando quais linhas aparecem

O WHERE já apareceu na Aula 7 (em UPDATE e DELETE) — no SELECT ele funciona do mesmo jeito, só que filtrando o que você vê, em vez de o que é alterado.

SELECT * FROM aluno WHERE turma = 'DS-2026';

Os operadores de comparação básicos:

OperadorSignificado
=igual a
<> ou !=diferente de
> / <maior que / menor que
>= / <=maior ou igual / menor ou igual

Você pode combinar condições com AND, OR e NOT:

SELECT * FROM emprestimo
WHERE data_emprestimo >= '2026-08-01' AND data_devolucao IS NULL;

E existem alguns operadores especiais, muito usados no dia a dia:

  • BETWEEN a AND b — está dentro de um intervalo. Ex.: WHERE preco BETWEEN 10 AND 50.
  • IN (lista) — bate com algum valor de uma lista. Ex.: WHERE turma IN ('DS-2026', 'DS-2027').
  • LIKE — compara texto com um padrão, usando % (qualquer sequência de caracteres) e _ (um único caractere). Ex.: WHERE nome LIKE 'Ana%' encontra "Ana", "Ana Paula", "Anabela".
  • IS NULL / IS NOT NULL — verifica se um campo está vazio (nunca use = NULL, isso não funciona em SQL).
Exemplo

Buscar todos os livros cujo título comece com "O": SELECT * FROM livro WHERE titulo LIKE 'O%';. Buscar empréstimos ainda não devolvidos: SELECT * FROM emprestimo WHERE data_devolucao IS NULL;.

8.4 — ORDER BY e LIMIT: ordenando e cortando o resultado

-- Ordena por nome, de A a Z (ascendente é o padrão)
SELECT * FROM aluno ORDER BY nome ASC;

-- Ordena do mais caro para o mais barato
SELECT * FROM livro ORDER BY titulo DESC;

-- Traz só os 5 primeiros resultados
SELECT * FROM aluno ORDER BY nome LIMIT 5;

ASC (crescente) é o padrão, então pode ser omitido; DESC (decrescente) sempre precisa ser escrito explicitamente. O LIMIT é muito usado junto com ORDER BY para perguntas do tipo "quais os 3 livros mais recentes?".

8.5 — Funções de agregação: resumindo os dados

Funções de agregação fazem um cálculo em cima de várias linhas e devolvem um único valor:

FunçãoO que faz
COUNT(*)Conta quantas linhas existem
SUM(coluna)Soma os valores de uma coluna numérica
AVG(coluna)Calcula a média dos valores
MIN(coluna)Encontra o menor valor
MAX(coluna)Encontra o maior valor
 
-- Quantos alunos existem cadastrados
SELECT COUNT(*) FROM aluno;

-- Qual o preço médio dos livros (se a tabela livro tivesse uma coluna preco)
SELECT AVG(preco) FROM livro;

8.6 — GROUP BY e HAVING: agrupando linhas parecidas

O GROUP BY agrupa linhas que têm o mesmo valor em uma coluna, e é quase sempre usado junto com uma função de agregação:

-- Quantos alunos existem em cada turma
SELECT turma, COUNT(*) AS total_alunos
FROM aluno
GROUP BY turma;

Se você quiser filtrar os grupos resultantes (e não as linhas originais), use HAVING em vez de WHERE — o WHERE roda antes do agrupamento, o HAVING roda depois:

-- Só as turmas que têm mais de 20 alunos
SELECT turma, COUNT(*) AS total_alunos
FROM aluno
GROUP BY turma
HAVING COUNT(*) > 20;
Fica de olho

WHERE filtra linhas, antes de agrupar. HAVING filtra grupos, depois de agrupar. É por isso que não dá para usar uma função de agregação (como COUNT) dentro de um WHERE — nesse ponto da consulta, os grupos ainda nem existem.

8.7 — A ordem lógica de um SELECT completo

Quando você usa vários desses recursos juntos, existe uma ordem que o MySQL espera:

SELECT colunas
FROM tabela
WHERE condição
GROUP BY coluna
HAVING condição_do_grupo
ORDER BY coluna
LIMIT quantidade;
Exemplo completo

"Quais são as 3 turmas com mais alunos, entre as que têm mais de 5 alunos, ordenadas da maior para a menor?"

SELECT turma, COUNT(*) AS total_alunos
FROM aluno
GROUP BY turma
HAVING COUNT(*) > 5
ORDER BY total_alunos DESC
LIMIT 3;
O que ainda falta

Repare que, até aqui, toda consulta busca dados de uma tabela só. Mas o empréstimo guarda só o id_aluno e o id_livro — não o nome do aluno nem o título do livro. Para juntar informação de várias tabelas ao mesmo tempo (por exemplo, "mostre o nome do aluno e o título do livro de cada empréstimo"), vamos precisar do JOIN, assunto de uma aula futura.
