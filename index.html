Prancha 01 / 04 — Bloco 1

Aula 1 — Introdução a Banco de Dados

Antes de escrever a primeira linha de SQL, você precisa entender três coisas: o que é um dado, onde ele mora, e por que existe uma linguagem inteira só para cuidar dele. É isso que fazemos nesta aula.

1.1 — Dado, informação e conhecimento não são a mesma coisa

É comum usar essas três palavras como sinônimas, mas em tecnologia da informação elas representam degraus diferentes de uma escada:

Exemplo

Dado é solto e sem contexto: 28. Informação é o dado organizado com significado: "a temperatura hoje é 28°C". Conhecimento é o que você faz com essa informação: "28°C é quente, vou levar uma roupa mais leve".

Um banco de dados trabalha na primeira camada dessa escada: ele armazena e organiza dados. Quem transforma esses dados em informação útil, na maioria das vezes, é a aplicação (o site, o sistema, o app) que está por cima do banco — mas para isso acontecer bem, o banco precisa estar muito bem estruturado. É aí que entra o trabalho do profissional de UC3.

1.2 — O que é um Banco de Dados e o que é um SGBD

Um banco de dados é, de forma simples, um conjunto organizado de dados relacionados entre si, guardados de forma permanente (não somem quando você desliga o computador). Pense numa grande "biblioteca de fichários": cada fichário guarda um tipo de informação (clientes, produtos, pedidos), e as fichas dentro dele seguem sempre o mesmo padrão.

Só que ninguém manuseia esses fichários "na mão". Existe um programa especializado só para isso: o SGBD (Sistema Gerenciador de Banco de Dados). É o SGBD que garante que dois usuários não vão bagunçar o mesmo dado ao mesmo tempo, que ninguém sem permissão vai ler informação sigilosa, e que, se a luz cair no meio de uma gravação, o dado não fica corrompido.

Analogia

Se o banco de dados é a biblioteca, o SGBD é o bibliotecário: ele sabe exatamente onde cada livro está, empresta e devolve livros de forma organizada, e não deixa duas pessoas rasgarem a mesma página ao mesmo tempo.

Exemplos de SGBDs que você vai ouvir falar (e usar) o curso inteiro: MySQL, PostgreSQL, Oracle Database e SQL Server. Todos eles "falam" a mesma língua de base — o SQL — mas cada um tem seus próprios sotaques e recursos extras.

1.3 — Banco de dados relacional × não-relacional

Existem duas grandes famílias de bancos de dados, e é essencial saber diferenciá-las logo no início do curso.

Banco de dados relacional

Organiza tudo em tabelas, como planilhas conectadas entre si. Cada tabela tem colunas fixas (nome, e-mail, telefone) e cada linha é um registro (uma pessoa, um produto). As tabelas se conectam por chaves estrangeiras — vamos estudar isso a fundo na Aula 3. É o modelo mais usado no mercado, e é o foco desta UC.

Banco de dados não-relacional (NoSQL)

Não obriga uma estrutura fixa de tabelas. Os dados podem ser guardados como documentos soltos (parecido com um arquivo JSON), pares de chave-valor, ou grafos de conexões. É muito usado quando os dados mudam de formato com frequência ou quando o volume é gigantesco (redes sociais, sensores IoT).

Analogia

O banco relacional é um arquivo de escritório: gavetas etiquetadas, pastas no mesmo formato, tudo padronizado. O banco não-relacional é uma caixa de sapatos onde cada papel pode ter um formato diferente — mais flexível, porém mais difícil de garantir que "está tudo igual".

CaracterísticaRelacionalNão-relacional
EstruturaTabelas fixas (linhas/colunas)Documentos, chave-valor, grafos
Linguagem padrãoSQLVaria por produto (sem padrão único)
Ideal paraDados estruturados, transações (bancos, ERPs)Dados variáveis, alto volume (redes sociais, logs)
ExemplosMySQL, PostgreSQL, OracleMongoDB, Redis, Cassandra

1.4 — Uma linha do tempo rápida do SQL

Entender de onde o SQL veio ajuda a entender por que ele é do jeito que é.

1970

O artigo de Edgar Codd

O matemático Edgar F. Codd, pesquisador da IBM, publica um artigo propondo o modelo relacional — a base teórica de tudo que estudamos nesta UC.

1974

Nasce o SEQUEL

Pesquisadores da IBM criam a linguagem SEQUEL (depois renomeada para SQL) para "conversar" com bancos relacionais usando frases parecidas com inglês comum.

1979

Primeiro SGBD comercial

A Oracle lança a primeira versão comercial de um SGBD relacional com suporte a SQL.

1986

Vira padrão internacional

O SQL se torna um padrão reconhecido pela ANSI e, depois, pela ISO — por isso o comando SELECT funciona quase igual em qualquer SGBD relacional do mundo.

Hoje

Ainda reinando

Mais de 50 anos depois, o SQL continua sendo a linguagem mais usada para lidar com dados estruturados — é isso que você vai dominar ao longo desta UC.

1.5 — Ferramentas que você vai usar no laboratório

Ao longo da UC3 você vai alternar entre algumas ferramentas. Não precisa decorar agora, só reconhecer o nome:

  • MySQL Workbench — interface visual para desenhar, consultar e administrar bancos MySQL.
  • SQL Developer e SQL Plus — ferramentas usadas para administrar bancos Oracle: uma com interface gráfica, outra em linha de comando.
  • Um software de modelagem, como o próprio MySQL Workbench ou o draw.io, para desenhar o banco antes de criá-lo de verdade (isso é assunto da Aula 3).
Fica de olho

Repare que já apareceram três siglas parecidas: SQL (a linguagem), SGBD (o programa que gerencia o banco) e MySQL (um SGBD específico que "fala" SQL). É normal confundir no início — releia esta seção se precisar.

Prancha 02 / 04 — Bloco 1

Aula 2 — Modelagem Conceitual do Banco de Dados

Nenhum engenheiro começa a construir um prédio sem antes desenhar a planta. Nesta aula, aprendemos a "plantar" um banco de dados no papel — entender o que o cliente precisa, documentar isso e preparar o terreno para o desenho do MER, que vem na próxima aula.

2.1 — Por que modelar antes de programar?

É tentador abrir o SGBD e sair criando tabelas "no improviso". O problema é que, sem planejamento, é quase certo que você vai precisar refazer tudo depois que perceber um relacionamento que esqueceu, ou uma informação que faltou.

Analogia

Construir um banco de dados sem modelar antes é como erguer uma casa sem planta: pode até ficar de pé, mas na hora de passar o encanamento você descobre que não sobrou espaço para os canos — e vai ter que quebrar parede. No banco de dados, "quebrar parede" significa migrar dados de produção, correndo o risco de perder informação.

Por isso, o processo de modelagem passa por três grandes etapas, do mais abstrato para o mais concreto: modelo conceitual (o que estudamos aqui — sem se preocupar ainda com o SGBD específico), modelo lógico (já pensando em tabelas e tipos de dado) e modelo físico (o banco realmente criado, com os comandos SQL rodados). Esta aula foca no primeiro passo.

2.2 — Levantamento de requisitos

Tudo começa conversando com quem vai usar o sistema — o stakeholder. O objetivo é descobrir os requisitos: o que o sistema precisa fazer e como ele precisa se comportar.

Os requisitos se dividem em dois tipos:

  • Requisito funcional: descreve uma ação que o sistema deve executar. Exemplo: "o sistema deve permitir cadastrar um novo aluno".
  • Requisito não funcional: descreve uma característica de qualidade, não uma ação. Exemplo: "o cadastro de aluno deve ser concluído em menos de 2 segundos" ou "os dados dos alunos devem ficar criptografados".
Exemplo prático

Imagine que você está modelando o banco de uma locadora de bicicletas. Ao entrevistar o dono, você anota:

  • Funcional: "preciso saber quais bicicletas estão emprestadas agora".
  • Funcional: "preciso cobrar uma multa se a bicicleta voltar atrasada".
  • Não funcional: "o sistema precisa funcionar mesmo sem internet na loja".

2.3 — Dicionário de dados

Depois de levantar os requisitos, é hora de listar, de forma organizada, cada informação (campo) que o sistema vai precisar guardar. Esse documento se chama dicionário de dados. Ele funciona como um "glossário oficial" do projeto: todo mundo da equipe consulta o mesmo documento para saber exatamente o nome e o formato de cada campo.

CampoTipoTamanhoDescrição
id_bicicletaInteiro—Identificador único da bicicleta
modeloTexto60Nome/modelo da bicicleta
statusTexto20"disponível", "emprestada" ou "manutenção"
valor_diariaDecimal6,2Valor cobrado por dia de aluguel

Repare que documentar assim, antes de criar qualquer tabela, evita um erro clássico de iniciante: chamar o mesmo tipo de dado de nomes diferentes em partes diferentes do sistema (por exemplo, id_bike em um lugar e bicicleta_id em outro).

2.4 — Teoria dos conjuntos aplicada a banco de dados

Pode parecer estranho falar de matemática numa aula de banco de dados, mas o modelo relacional inteiro nasceu de conceitos de teoria dos conjuntos. Uma tabela, no fundo, é tratada como um conjunto de linhas. Isso vai explicar, lá na frente, por que comandos SQL como UNION e INTERSECT têm esse nome:

  • União — junta os elementos de dois conjuntos, sem repetir.
  • Interseção — traz só os elementos que existem nos dois conjuntos ao mesmo tempo.
  • Diferença — traz os elementos que existem em um conjunto, mas não no outro.
Analogia

Imagine a lista de alunos que fazem Inglês e a lista de alunos que fazem Robótica. A união das duas listas é "todo mundo que faz pelo menos uma das duas". A interseção é "quem faz as duas ao mesmo tempo". A diferença (Inglês menos Robótica) é "quem faz só Inglês".

Guarde essa ideia — ela volta com tudo na Aula 8 do nosso curso, quando estudarmos JOINs de verdade em SQL.

2.5 — Tipos de dados e domínio de um atributo

Cada informação que vamos guardar tem um tipo (número, texto, data...) e um domínio — ou seja, os valores que ela pode legitimamente assumir. Definir o domínio ainda na modelagem conceitual evita bancos de dados "bagunçados" no futuro.

Exemplo

O campo status da nossa tabela de bicicletas tem domínio limitado: só pode ser "disponível", "emprestada" ou "manutenção" — nunca, por exemplo, "amarela". Já decidir isso agora evita que, no futuro, alguém digite valores inconsistentes ali dentro.

2.6 — Integridade referencial (uma primeira olhada)

Integridade referencial é o princípio que garante que as conexões entre tabelas nunca fiquem "quebradas". Se um empréstimo de bicicleta referencia a bicicleta de id_bicicleta = 12, a integridade referencial garante que essa bicicleta 12 realmente existe na tabela de bicicletas — e impede, por exemplo, que alguém apague a bicicleta 12 enquanto ela ainda está emprestada.

Vamos aprofundar esse conceito na Aula 3, quando falarmos de chaves primárias e estrangeiras — por enquanto, guarde a ideia central: nenhuma referência pode apontar para o nada.

Prancha 03 / 04 — Bloco 1

Aula 3 — Modelo Entidade-Relacionamento (MER)

Chegou a hora de transformar o dicionário de dados e os requisitos da Aula 2 em um desenho. O MER é o "mapa" visual do banco: mostra quais informações existem, como elas se agrupam e como se conectam — tudo isso antes de criar uma única tabela de verdade.

3.1 — O que é uma entidade

Uma entidade representa algo do mundo real (ou até abstrato) sobre o qual queremos guardar dados: um Aluno, um Produto, um Pedido, uma Bicicleta. No desenho do MER, cada entidade vira um retângulo. Mais para frente, cada entidade normalmente vira uma tabela no banco de dados de verdade.

Exemplo

No sistema da nossa locadora de bicicletas, entidades naturais seriam: Bicicleta, Cliente e Empréstimo.

3.2 — Atributos: o que a entidade "sabe" sobre si mesma

Cada entidade tem atributos: as informações que descrevem aquela entidade. A entidade Cliente pode ter os atributos nome, CPF, telefone. Existem alguns tipos especiais de atributo que vale a pena conhecer:

  • Atributo simples: não pode ser dividido. Ex.: CPF.
  • Atributo composto: pode ser dividido em partes menores. Ex.: endereço pode virar rua, número, cidade.
  • Atributo multivalorado: pode ter mais de um valor para a mesma entidade. Ex.: um Cliente pode ter vários telefones.
  • Atributo derivado: pode ser calculado a partir de outro. Ex.: idade pode ser derivada da data de nascimento.

3.3 — Chaves: como identificar um registro sem confusão

Numa turma de 40 alunos, pode existir mais de um "João Silva". Por isso, toda entidade precisa de um jeito de identificar cada registro de forma única — isso se chama chave.

  • Chave candidata: qualquer atributo que poderia, sozinho, identificar o registro de forma única. Um aluno pode ter tanto o CPF quanto a matrícula como chaves candidatas.
  • Chave primária: a chave candidata que escolhemos oficialmente para representar o registro. Geralmente é um código simples, como id_aluno.
  • Chave estrangeira: um campo que "empresta" a chave primária de outra entidade, criando a conexão entre as duas. É assim que um Empréstimo sabe a qual Bicicleta ele se refere.
Exemplo

Na tabela Empréstimo, o campo id_emprestimo é a chave primária dela mesma. Os campos id_bicicleta e id_cliente, dentro dessa mesma tabela, são chaves estrangeiras — eles apontam para a chave primária das tabelas Bicicleta e Cliente.

3.4 — Relacionamentos e seu grau

Um relacionamento é a conexão entre duas (ou mais) entidades — no desenho, vira um losango ligando os retângulos. O grau do relacionamento indica quantas entidades participam dele:

  • Unário: a entidade se relaciona com ela mesma. Ex.: um Funcionário é "supervisor" de outro Funcionário.
  • Binário: o mais comum — duas entidades se relacionam. Ex.: Cliente faz Empréstimo.
  • Ternário: três entidades participam do mesmo relacionamento. Ex.: um Professor ministra uma Disciplina em uma Turma.

3.5 — Cardinalidade: quantos para quantos?

A cardinalidade é uma das partes mais importantes (e mais cobradas em prova!) do MER. Ela responde: "quantos registros de uma entidade podem se conectar a quantos registros de outra?"

TipoDescriçãoExemplo
1:1 (um para um)Um registro de A se relaciona com no máximo um registro de B, e vice-versa.Uma Pessoa tem um Passaporte; um Passaporte pertence a uma Pessoa.
1:N (um para muitos)Um registro de A pode se relacionar com vários registros de B, mas cada B se liga a apenas um A.Um Cliente pode ter vários Empréstimos; cada Empréstimo pertence a um único Cliente.
N:N (muitos para muitos)Vários registros de A se relacionam com vários registros de B.Um Aluno pode cursar várias Disciplinas; cada Disciplina tem vários Alunos.
Fica de olho

Relacionamentos N:N não podem ser implementados diretamente numa tabela — eles exigem a criação de uma tabela associativa (também chamada de tabela de junção) para funcionar no banco físico. Vamos ver isso na prática mais adiante no curso.

3.6 — Entidades fortes e fracas

Uma entidade forte existe por conta própria e tem sua própria chave primária (ex.: Cliente). Uma entidade fraca só existe se estiver associada a uma entidade forte — ela depende da outra para "fazer sentido". Ex.: os Dependentes de um funcionário só existem no sistema porque o Funcionário existe; se o Funcionário for removido, os Dependentes dele também deixam de fazer sentido.

3.7 — Mini estudo de caso: sistema de biblioteca

Vamos aplicar tudo o que vimos num exemplo completo. Imagine que a biblioteca da escola pediu um sistema simples de empréstimo de livros. Levantamos as seguintes entidades e relacionamentos:

Estudo de caso

Entidades: Livro (id_livro, título, autor), Aluno (id_aluno, nome, turma), Empréstimo (id_emprestimo, data_emprestimo, data_devolucao).

Relacionamento: um Aluno realiza vários Empréstimos (1:N), e um Empréstimo se refere a um único Livro por vez (1:N entre Livro e Empréstimo).

Chaves estrangeiras: a tabela Empréstimo carrega id_aluno e id_livro como chaves estrangeiras.

Prática guiada — desenhe você mesmo

Pegue papel e caneta (ou o software de modelagem que preferir) e desenhe o MER completo do sistema de biblioteca acima, incluindo entidades, atributos, chaves e a cardinalidade de cada relacionamento. Isso será revisado como prática da Aula 3 antes de seguirmos para a Aula 4.

Prancha 04 / 04 — Bloco 1

Aula 4 — Normalização

Fechando o Bloco 1: agora que sabemos desenhar entidades e relacionamentos, precisamos garantir que as tabelas resultantes sejam "saudáveis" — sem repetição desnecessária de dados e sem armadilhas escondidas. Esse processo de organização se chama normalização.

4.1 — O problema da redundância

Imagine a tabela abaixo, construída "no impulso", sem nenhuma modelagem prévia — um erro clássico de quem pula direto para o SQL sem passar pela Aula 2 e pela Aula 3:

id_pedidoclientetelefone_clienteprodutopreço
1Ana Souza51 9999-0001Mouse45,00
2Ana Souza51 9999-0001Teclado120,00
3Ana Souza51 9999-0001Monitor800,00

Repare no problema: o nome e o telefone da Ana estão redundantes — repetidos em toda linha. Se o telefone da Ana mudar, alguém vai precisar atualizar as três linhas. E se esquecer uma? O banco fica com dados contraditórios.

4.2 — Dependência funcional: a base da normalização

Dizemos que existe uma dependência funcional quando, sabendo o valor de um atributo, conseguimos determinar o valor de outro. No exemplo acima, o telefone_cliente depende do cliente — não do pedido. É essa dependência "no lugar errado" que gera a redundância.

4.3 — As três anomalias

Tabelas mal normalizadas sofrem de três tipos de problema, conhecidos como anomalias:

  • Anomalia de inserção: para cadastrar um cliente novo que ainda não comprou nada, você não tem "onde" colocá-lo, porque a tabela só existe atrelada a pedidos.
  • Anomalia de atualização: mudar o telefone da Ana exige atualizar três linhas — esquecer uma gera inconsistência.
  • Anomalia de exclusão: se a Ana cancelar o único pedido dela (id 1), e essa linha for apagada, perdemos o telefone dela junto — mesmo que ela continue sendo cliente.

4.4 — Primeira Forma Normal (1FN)

Uma tabela está na Primeira Forma Normal quando cada célula guarda um único valor (nada de "listas dentro da célula") e não existem grupos de colunas repetidas.

Antes (viola a 1FN)

telefones: "51 9999-0001, 51 9999-0002" — dois telefones espremidos numa célula só.

Depois (respeitando a 1FN)

Cria-se uma tabela separada Telefone (id_telefone, id_cliente, numero), com uma linha para cada telefone. Assim cada célula guarda um único valor, e um cliente pode ter quantos telefones precisar.

4.5 — Segunda Forma Normal (2FN)

Para estar na Segunda Forma Normal, a tabela precisa, primeiro, já estar na 1FN. Além disso, todo atributo precisa depender da chave primária inteira — não apenas de parte dela. Esse problema só aparece quando a chave primária é composta por mais de um campo.

Exemplo

Imagine uma tabela com chave composta (id_pedido, id_produto) guardando também o nome_produto. O nome_produto depende só de id_produto, não do id_pedido — ou seja, depende de parte da chave, não da chave inteira. Isso viola a 2FN. A solução é mover nome_produto para uma tabela Produto separada.

4.6 — Terceira Forma Normal (3FN)

Para estar na Terceira Forma Normal, a tabela precisa já estar na 2FN, e nenhum atributo pode depender de outro atributo que não seja a chave — isso se chama dependência transitiva.

Exemplo

Numa tabela Aluno (id_aluno, nome, id_cidade, nome_cidade), o campo nome_cidade depende de id_cidade, que por sua vez depende de id_aluno — uma dependência em cadeia. Isso viola a 3FN. A solução é criar uma tabela Cidade separada (id_cidade, nome_cidade), e a tabela Aluno guarda só a chave estrangeira id_cidade.

4.7 — Resultado final: a tabela do pedido, normalizada

Aplicando as três formas normais no nosso exemplo inicial, chegamos a três tabelas enxutas e sem redundância:

ClientePedidoProduto
id_cliente, nome, telefoneid_pedido, id_cliente (FK), id_produto (FK)id_produto, nome, preço

Agora, se o telefone da Ana mudar, atualiza-se em um único lugar. Se ela cancelar um pedido, o cadastro dela como cliente continua intacto. É essa robustez que a normalização entrega.

Nota rápida sobre "desnormalizar"

Em sistemas com altíssimo volume de leitura, às vezes engenheiros optam por desnormalizar propositalmente parte do banco (reintroduzir alguma redundância controlada) para ganhar velocidade de consulta. Isso é um assunto avançado — por enquanto, o mais importante é dominar bem a normalização "pelo livro" antes de aprender quando quebrar a regra.
